会的。在 Flutter 中，状态提升后，如果父组件（持有状态的一方）调用 `setState`，**默认情况下，它的所有子组件（包括不需要更新的那些）的 `build` 方法都会被执行**。

### 为什么会这样
这是 Flutter 的基本重建机制。当父组件的状态改变并调用 `setState` 时，框架会将该父组件标记为“脏”（dirty），并计划在下一帧重新构建它。在重建父组件时，它会重新执行 `build` 方法，并生成一棵新的 Widget 子树。在这个过程中，所有子组件的 `build` 方法默认都会被再次调用，无论它们依赖的数据是否真的发生了变化。

### 一个直观的例子
回到之前计数器的例子。假设 `CounterPage` 除了展示计数的 `CountDisplay` 和按钮，还有一个完全静态的、与计数无关的 `HeavyWidget`（比如一个复杂的图表）。

如果你把状态放在 `CounterPage` 的 `State` 里，每次点击“加一”并调用 `setState` 时：
1. `CounterPage` 重建。
2. `CountDisplay` 重建（这是必要的）。
3. `IncrementButton` 重建。
4. **`HeavyWidget` 也会重建**，尽管它的 UI 和计数毫无关系。如果 `HeavyWidget` 的 `build` 很耗时，这就是纯粹的浪费。

### 如何避免这种浪费
如果不需要更新的子组件重建开销较大，可以通过一些手段来“跳过”它们：

1.  **把子组件提取出来，并让它不依赖父组件的状态**：如果 `HeavyWidget` 被定义成一个独立的 `StatelessWidget`，并且它的构造函数里没有任何来自父状态的数据，那么当父组件重建时，虽然 `HeavyWidget` 的新实例会被创建，但只要它是 `const` 构造函数或者框架判断其配置未变，它的内部 `build` 可能会被跳过。不过，最可靠的方式还是下面的几种。
2.  **使用 `const` 构造函数**：如果子组件是完全静态的，用 `const` 实例化它。当父组件重建时，如果新的 `const` 实例与旧的在运行时是同一个对象，框架会跳过该子树的重建。
3.  **拆分组件，隔离状态**：这是最根本的优化。不要把不相关的 UI 和状态放在同一个 `StatefulWidget` 里。把 `HeavyWidget` 放在一个不随计数变化的父组件下，或者把它封装成一个独立的、自带状态管理的组件，这样 `CounterPage` 的 `setState` 就不会波及它。
4.  **使用更精细的状态管理方案**：当 `setState` 的重建范围过大成为问题时，就是考虑引入 `Provider`（配合 `Selector`）、`Riverpod` 或 `Bloc` 等方案的时机。它们能让你精确地指定“只有关心某部分数据的组件才重建”，从而避免这种“连坐”。

所以，状态提升本身并不“导致”浪费，但它把 `setState` 的作用点提高了。如果父组件的子树很大且包含无关内容，每次状态更新都会带来不必要的 `build` 开销。意识到这一点，并有意识地把 Widget 拆小、隔离，是使用状态提升时需要注意的性能关键。
